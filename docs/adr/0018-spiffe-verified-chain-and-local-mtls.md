# ADR 0018: SPIFFE Verified-Chain Identity and Local mTLS

Status: Accepted

Date: 2026-07-16

## Context

Stage 2 introduces real internal identity endpoints called by `telegram-bot`. These endpoints must not rely on a private Docker network, spoofable headers, DNS names, Common Name, or unverified peer certificates for service authorization.

Local Compose also needs to exercise the same mTLS path without depending on OpenSSL being installed on the developer machine.

## Decision

- Internal service identity is accepted only from `tls.ConnectionState.VerifiedChains[0][0].URIs`.
- The URI must match `spiffe://vpn-service/ns/{environment}/sa/{service}` exactly.
- DNS SAN and Common Name are never authorization inputs.
- Internal HTTP servers use TLS 1.3 and require client certificates from the configured platform CA.
- Default local Compose uses generated short-lived development certificates from `secrets/dev-mtls`. ADR 0027 supersedes the original direct-bind detail: a network-isolated init container stages an allowlisted subset into per-owner named volumes before non-root services start.
- Development certificates are generated by the Go tool `tools/devmtls/cmd/devmtls`; no OpenSSL dependency is required.
- The identity-service container healthcheck uses a separate local client certificate so health checks do not weaken server mTLS.
- `dev-insecure` remains available only for isolated local experiments, is rejected outside `APP_ENV=local`, and is not used by the default Compose smoke path.

## Consequences

- `telegram-bot /readyz` checks Redis and an mTLS request to `identity-service /livez`.
- Plain HTTP calls to identity-service are not part of default local Compose.
- Generated local certificate material is ignored by Git and allowed only under `secrets/dev-mtls` in the local secret scan configuration.
- Production certificate issuance, rotation, and revocation remain future deployment work.
